# V0.3-D3 扫描轨预研：紫金扫描主表勘查与 OCR 通道选型（2026-09-07）

对应设计方案：§14 引擎选型、§13 证据链多通道、§18 先有真实答案再谈覆盖。
路线：2026-09-07 用户拍板——港股繁英低需求（Docling 移除）、**扫描覆盖高优先级**；
"把其他表纳入"= 先广度后深度（D1/D2 已落地）。D3 = 扫描轨**预研**（本文件不含 OCR 跑批结论，
不承诺覆盖率）。

## 1. 目标与范围

- 目标输入：A 股年报中**扫描/纯图页**（原生文字层缺失或不可信）的六张法定主表及其它附表。
- 本阶段交付：①确认扫描主表所在页与证据状态；②核对本机可用 OCR 引擎；③给出扫描通道选型与
  验收样本；④明确 OCR 数字的证据资格边界（single_channel，不升 facts）。
- 不承诺：首版自动解决任意扫描精度；不在未有人工真值前报告覆盖率。

| 主表 0 facts 根因 | 主表为扫描图页，无可靠原生文字 → M1/M2 主表规则无输入 |

## 3. 本机 OCR 引擎勘查（2026-09-07）

| 引擎 | 状态 | 备注 |
|---|---|---|
| **MinerU CLI** | ✅ 已装（3.4.5，模型 PDF-Extract-Kit-1.0 已缓存） | 已用于无框线表结构候选与矢量轮廓复核；自带 OCR 后端 |
| PP-StructureV3 / PaddleOCR / paddle | ❌ 未装 | 需装 paddlepaddle（体量大、MPS 验证成本），当前未装 |
| docling / pymupdf / rapidocr / tesseract | ❌ 未装 | — |

**结论**：本机可用的**第一条扫描 OCR 通道 = 已装 MinerU OCR**（零新增依赖，跑 113–128 页即可产出
OCR 文字/表格候选，隔离为 `single_channel`，绝不进 facts）。

## 4. 选型建议（分两通道，避免共享模型）

- **第一扫描通道（近期，零安装）**：MinerU OCR 跑紫金 113–128 → OCR 表格网格/文字候选 → adapter
  进统一结构（复用 `run_tableslice`/`run_parse --mineru-content` 通道）→ 登记为 `single_channel`
  不可引用候选，进 `复核/` 与 pending 签核。
- **第二独立通道（远期，需安装）**：PP-StructureV3。设计 §13.1 要求第二引擎与第一引擎**不共享
  模型**才能构成有效对照；当扫描轨正式立项并整份跑批时再安装（paddlepaddle+模型，锁版本、离线），
  用真实样本验收。
- 若第二通道采用与 MinerU 同源的引擎，只能算同源复检，不算独立通道（记录为边界）。

## 5. 验收样本（先有真实答案）

- 首选人工标注页：紫金 **113–128 中覆盖六张主表表头+数据的页**（预计 6–10 页），每页标注：
  表题/币种单位/行标签/列期间头/逐格数值；
- 判读指标：主表页 OCR 的（表检测、文字行、数值精确）按页上报；OCR 候选与人工真值不一致→
  `single_channel` 不进 facts；任何关键错配阻止发布。
- 待第二独立通道 + 逐格一致 + 人工签核（`run_signoff`）后，才谈 OCR 数值升格。

## 6. MinerU OCR 跑批观测（2026-09-07 已执行，第一扫描通道）

命令（MinerU 3.4.5，-s/-e 为 0 起始）：
`mineru -p <紫金2025年报.pdf> -o <out> -b pipeline -m auto -s 112 -e 127 -l ch`
产物归档：`tests/_research_packages/_D3_mineru_main/auto/*.md + *_content_list.json`（gitignored）。

| 观测项 | 结果 |
|---|---|
| 页范围 | 物理 113–128（16 页）全部跑通，无失败 |
| 表体恢复 | **16 个 `<table>` 全部含数值**（如资产负债表表体 34 行/82 数字 cell），行标签+附注号+2025/2024 列基本完整 |
| **表题** | **标题（合并资产负债表等）未被 OCR 进文本**；只出现“2025年度/2024年度/后附财务报表附注…”零散文本 → 表→六类主表映射需靠表体结构线索（资产/负债首行、科目锚点）或另做表题区域 OCR |
| 数字资格 | 全部为 MinerU **单通道 OCR 值**：`single_channel`，不可引用/计算；需第二独立通道+逐格一致+人工签核 |
| 伪影 | 可见部分页尾“后附财务报表附注…”、年份碎文本、签字栏（“主管会计工作负责人”重复）等非表格杂散项，须按页过滤 |

结论：**MinerU OCR 可作为紫金扫描主表的第一个可行 OCR 通道**（表体+数值可恢复）；表题缺口与
`single_channel` 资格是进入语义层的两道硬门。

## 8. 表题缺口处理：表体结构线索路由工具（2026-09-07）

新增探针 `scripts/route_ocr_main_statements.py`：用**强制锚点 + 计数**给 OCR 表出六类主表
*candidate* 路由（利润表/现金流表/资产负债(左右半页)/权益变动表 + 合并 scope 候选），纯标准库、
单测覆盖（`tests/test_route_ocr.py`，全套 106 项绿）。

- **页级绑定**（`--content-list` 模式）：MinerU `*_content_list.json` 每页多子项，
  `type=='table'` 项带 `table_body`(HTML) + `page_idx`（切片内 0 起始）→ 物理页 =
  `first_physical + page_idx`，比 md 图片行计数可靠（md 一物理页可多张子图致页漂移）。
- **对紫金 16 张 OCR 表应用结果**：**14/16 已候选路由**——资产负债资产侧 p113/122、利润表
  p116/124（+OCI 续段 p117）、权益变动表 p118/119/125/126、现金流量表 p120/121/127/128、
  资产负债权益侧 p123（母公司，附注十七）。
- **剩余 p114/115**（合并资产负债表"负债和股东权益"右侧两页）未命中：OCR 未出
  `负债合计/股东权益合计` 小计行或行被拆断 → 留待人工核对。
- **规则修正教训**：①权益变动表须先有 上年年末/本年年初/本年增减变动（否则"权益侧"页误判）；
  ②资产负债右页支持"股东权益"口径（紫金用 股东权益 非 所有者权益）；③现金流表按节分页、
  OCR 有"产生的/使用的"变体；④利润表"其他综合收益"续段页单列。
- 全程 OCR 数值 single_channel，本工具只给 candidate 路由、不碰数值、不升 facts。
